# 3단계 — 보드와 핵심 게임 명령

## 단계 목표

서버 보드 스냅샷을 UI용 고정 슬롯 배열로 투영하고, 아이템 생성과 머지를 서버
revision 계약에 연결했습니다. 서버 저장소와 `/api/v1` 계약은 변경하지 않았습니다.

## 보드 표현

`BoardPresentationState`는 서버의 `width × height`와 `items`를 읽어 슬롯 배열을 만듭니다.
빈 슬롯은 표시용 빈 값으로만 표현하며 아이템 종류, 레벨 또는 합성 결과를 추론하지
않습니다. 잘못된 슬롯 인덱스가 응답에 있어도 배열 경계를 넘지 않게 무시합니다.

## 명령 흐름

`BoardCommandService`는 `GameStateStore`의 마지막 서버 revision을 요청 DTO에 넣습니다.

- 머지: `expectedRevision`에 현재 보드 revision 사용
- 생성: `expectedBoardRevision`과 `expectedEconomyRevision`을 함께 사용
- 성공: 서버가 반환한 보드·경제 스냅샷만 상태 저장소에 적용
- 409: 변경 요청을 반복하지 않고 보드와 경제를 다시 조회
- 그 외 실패: 기존 로컬 스냅샷을 임의 수정하지 않고 분류된 오류 반환

409 후 반환되는 `ConflictResynchronized`는 자동 성공이 아닙니다. 화면은 최신 보드에서
원래 선택 슬롯과 사용자 의도가 여전히 유효한지 확인한 뒤 새 명령을 만들어야 합니다.

## 보안과 서버 권위

클라이언트는 생성 시 에너지 1 감소, 머지 후 아이템 레벨 증가, 새 revision 값을 미리
확정하지 않습니다. 모든 값은 서버 성공 응답을 통해서만 갱신됩니다. 토큰과 관리자 API
관련 코드는 이 계층에 포함하지 않습니다.

- 컴파일 성공, C# 오류 0개, 경고 0개
- EditMode 8개 통과, 실패 0개, 건너뜀 0개
- PlayMode 6개 통과, 실패 0개, 건너뜀 0개
- 보드 슬롯 투영, 머지 revision 전달과 서버 응답 적용 검증
- 생성의 보드·경제 revision 동시 전달과 서버 스냅샷 적용 검증
- 409 시 변경 호출 1회 유지 및 최신 보드·경제 조회 검증

## 다음 단계 제안

4단계에서는 경제 조회, 일일 보상, 퀘스트 조회와 멱등 보상 수령 명령을 추가합니다.
